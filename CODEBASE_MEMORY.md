# Anxiety State Monitor - Codebase Memory

## Project Overview
Real-time physiological monitoring system that reads HR and GSR from HC-05 Bluetooth, processes through a multi-stage pipeline, and serves a live Flask dashboard.

**Entry point:** `app.py` → loads config, starts reader, runs Flask on port 5000

## Architecture Pipeline
```
Sensor/Mock → BluetoothReader → DataPipeline → BaselineTracker → compute_features()
    → RulesEngine → MlPredictor → FusionEngine → PredictionSmoother → StateMachine
    → PatternDetector → AlertSystem → AnxietyStateService snapshot → Flask API
```

## Data Flow Details

### Input Parsing (bt_reader.py)
Accepts: `GSR:520,HR:72` | `HR:72 GSR:520` | `BSP:520,BPM:72` (any order, int/float)
Ignores: lines with "finger", "place", "wait" → surfaces as sensor_warning

### Pipeline (pipeline.py)
- Rejects: HR ∉ [40, 210], GSR ∉ [0, 1200]
- Moving average: 3 samples
- Sliding window: 30 seconds
- Returns smoothed (hr, gsr) only after MA buffer fills

### Baseline (features.py:BaselineTracker)
- Calibration: 30s of stable samples (std_hr ≤ 15, std_gsr ≤ 50)
- If fixed_hr + fixed_gsr set → instant calibrated
- Optional drift adaptation (disabled by default, alpha=0)
- Buffer slides forward until stable period found (95% of calibration time + ≥10 samples)

### Features (features.py:compute_features)
Requires: ≥10 samples, ≥10s window duration
Outlier removal: HR clamp [40,180], GSR IQR (1.5×)
Rejects if >50% outliers
Returns: mean_hr, std_hr, hr_trend, mean_gsr, std_gsr, gsr_trend, delta_hr, delta_gsr, stress_index, confidence

Confidence scoring (compute_feature_quality_score):
- Volume (40%): raw samples / 60 optimal
- Noise (40%): min(valid_hr_ratio, valid_gsr_ratio)
- Variance (20%): HR std >15 loses points, GSR std >60 loses points

Stress index: `delta_hr * w_hr + delta_gsr * w_gsr` (defaults: 1.0, 0.05)

### Rules (rules.py)
- ANXIETY: delta_hr > 12 AND delta_gsr > 80 (unless ACTIVE: hr_trend > 0.005 AND delta_gsr < 25)
- ACTIVE: hr_trend > 0.005 AND delta_gsr < 25
- STRESS: delta_hr > 6 OR delta_gsr > 40
- Recovery: prev ∈ {STRESS,ANXIETY} AND hr_trend < -0.003 → CALM if deltas low, else STRESS
- Confidence < 0.5: ANXIETY→STRESS, STRESS→CALM

Thresholds (configurable via ThresholdConfig):
- anxiety_delta_hr: 12.0, anxiety_delta_gsr: 80.0
- stress_delta_hr: 6.0, stress_delta_gsr: 40.0
- activity_hr_trend: 0.005, activity_gsr_ceiling: 25.0
- recovery_hr_trend: -0.003

### ML (ml_predictor.py)
- Binary: CALM vs ANXIETY only
- Loads model.pkl + optional scaler.pkl
- Returns MlPrediction(label, probabilities, confidence)
- CLASS_NAMES = ["CALM", "STRESS", "ANXIETY", "ACTIVE"] (but model only outputs CALM/ANXIETY)

### Fusion (fusion.py)
- ML unavailable → rules
- ML=ANXIETY + effective_conf ≥ 0.75 → ANXIETY (source: "ml" or "both")
- ML=CALM or low conf → rules (source: "rules")
- Effective confidence = ml_confidence * feature_confidence

### Smoother (prediction_smoother.py)
- Majority vote over 7 labels
- Hysteresis: need 2 consecutive majority changes to switch
- Resets pending streak on agreement

### FSM (state_machine.py)
| Transition | Condition | Hold |
|------------|-----------|------|
| CALM → STRESS | input=STRESS | 3s |
| STRESS → ANXIETY | input=ANXIETY | 3s |
| STRESS → CALM | input=CALM | 3s |
| ANXIETY → RECOVERY | input∈{CALM,STRESS} + hr_trend < 0 | 5s |
| RECOVERY → CALM | input=CALM | 5s |
| CALM → ANXIETY (emergency) | input=ANXIETY + stress_index > 12 | 3s |

ACTIVE normalized to STRESS at FSM entry
Candidate tracking: resets timer if input changes, commits when hold time met

### Patterns (pattern_detector.py)
- UNSTABLE_SIGNAL: confidence < 0.4 OR std_hr > 15 OR std_gsr > 50
- RAPID_STRESS_SPIKE: delta_hr +8, delta_gsr +0.5 in 5-10s window
- GRADUAL_STRESS_BUILD: stress_index +1.5 over 20-40s
- SLOW_RECOVERY: -0.5 < hr_trend < -0.01
- NORMAL: fallback
- Buffer: 60s rolling window of (timestamp, FeatureVector)

### Alerts (alert_system.py)
- HIGH: ANXIETY > 10s + confidence > 0.6
- MEDIUM: STRESS > 20s OR RAPID_STRESS_SPIKE
- LOW: GRADUAL_STRESS_BUILD OR SLOW_RECOVERY
- NONE: else
- Tracks state duration independently from FSM

## API Contract
**GET /** → index.html
**GET /data** → JSON snapshot (no-cache headers)
**GET /stream** → SSE (1 JSON/sec)

Session lifecycle (all additive):
**POST /session/start** `{label?}` → 201 `{session_id, phase, label}` | 409 `session_active`
**POST /session/end** → 200 `{session_id, report_url, reliability}` | 409 `no_active_session`
**POST /session/calibration/restart** → 200 `{session_id, attempts}` | 409 `not_calibrating`
**POST /session/intervention** `{event, technique?, planned_duration_s?, cycles_completed?}` → 200 `{status, index}` | 400 `invalid_event` | 409 `no_active_session`
**POST /session/exercise** `{event}` → 200 (back-compat alias, forwards to the intervention handler)

Reports:
**GET /sessions** → newest-first list (id, label, started_at_iso, duration_s, reliability, peak_state, episode_count, status), capped at 50
**GET /session/&lt;id&gt;/report** → report JSON; the running session returns the live partial (`status: "partial"`, `reliability: "PARTIAL"`)
**GET /session/&lt;id&gt;/report.html** → standalone offline HTML attachment
**GET /session/&lt;id&gt;/report.csv** → this session's raw log rows
Session ids are validated against `^[0-9]{8}-[0-9]{6}-[0-9a-f]{4}$` before any filesystem access; anything else 404s.

Snapshot fields: server_time, hr, gsr, state, rule_state, ml_state, fused_state, fusion_source, connection, connection_detail, sensor_warning, baseline_hr, baseline_gsr, features{}, window_samples, calibrated, pattern, alert, prediction{}, **session{}**

`session` block: phase, id, label, started_at, elapsed_s, monitored_s, recording, evaluating,
`calibration{method, progress, elapsed_s, target_s, stable, stalled, paused, attempts}`,
`live{reliability, coverage_pct, episodes, warnings, interventions, peak_alert, intervention_active}`.
In IDLE, id/label/started_at/calibration/live are null and recording/evaluating are false.

## Session Reports (data/sessions/)
- `<id>.json` — immutable final report, written on end_session (tmp + os.replace)
- `<id>.partial.json` — checkpoint every 10s, deleted on a clean end; finalized as
  `status: "interrupted"` on the next boot if the backend stopped mid-session
- Reliability grades: GOOD / LIMITED / INSUFFICIENT (PARTIAL while running). An INSUFFICIENT
  report keeps identity/quality/baseline and nulls the rest with `unavailable` reasons.
- Any value that cannot be computed is null plus an `unavailable` entry — never 0, never blank.

## CSV Log (data/logs/physio_log.csv) — schema v2
Columns: timestamp_iso, session_id, session_phase, hr, gsr, raw_line, rule_state, ml_state, fused_state, final_state, connection, exercise_event
- Rows outside a recording phase carry an empty `session_id` and the current phase
- A log whose header predates v2 is rotated to `physio_log.pre_sessions.csv` on boot
  (appending columns in place would have misaligned every earlier row)
- Logs every 1s (configurable)
- During warmup/calibration, processed columns can be blank

## Device Usage Workflow
1. Wear sensor with stable skin contact
2. Power on device (2 beeps = firmware ready)
3. Wait for Bluetooth connection (green status bar)
4. Stay still during baseline calibration (~30s)
5. Keep hand still entire session (no accelerometer for motion compensation)

Buzzer: 1 buzz/second = data point recorded
Movement causes false HR spikes → misclassification

## Connection States
- `starting`, `connecting`, `connected`, `mock`, `no_data`, `disconnected`, `error`
- Sensor warnings separate: "Place finger on sensor", etc.

## Implementation Notes
- Thread safety: `threading.Lock` in AnxietyStateService
- Path handling: `backend/paths.py` resolves relative to repo root
- CORS enabled for cross-origin API access
- Feature confidence is scored against a full sliding window (~30 samples); it previously
  divided by 60 and could never exceed 0.8, starving every downstream confidence gate
- No database - state in memory, CSV logs
- `reset_session()` is the session-boundary primitive; `start_session()` reuses it via
  `_reset_session_locked()`. Session control is exposed through POST /session/start and /session/end

## Known Issues / Limitations
1. ML model is binary (CALM/ANXIETY) but rules/FSM are multi-state
2. The live dashboard still does not surface pattern/alert/features directly; they are
   recorded per session and shown in the session report instead
3. No motion compensation (no accelerometer)
4. Dashboard depends on Chart.js CDN (not fully offline)
5. Repo contains generated artifacts/cache (__pycache__, debug files)
6. No formal unit/integration test suite
7. ml/scaler.pkl is a leftover from an earlier pipeline; train.py fits on raw features and
   MlPredictor now ignores an unmarked scaler (applying it gave 0% ANXIETY recall)
8. The ML tier corroborates the rules' ANXIETY but does not promote STRESS to ANXIETY:
   its confidence does not separate mild elevation from full arousal
   (override available via ANXIETY_ML_ALLOW_ESCALATION=1)
9. The reported state reflects a 30 s trailing window, so it lags true physiology by
   roughly 20 s on onset and 30 s on recovery
10. One backend instance per CSV log: concurrent instances interleave rows (no lock file)

## Training Pipeline Details (ml/train.py)
1. Loads raw HR/GSR/label from training_data.csv
2. Builds real DataPipeline + BaselineTracker (matching production)
3. Simulates chronological time at 1 Hz (monkey-patches time.time)
4. Pushes raw data through same smoothing/window logic
5. Computes production feature vectors via compute_features()
6. 80/20 train/test split (shuffle=True, random_state=42)
7. RandomForestClassifier: n_estimators=100, max_depth=5, min_samples_split=10, min_samples_leaf=5, class_weight="balanced", random_state=42
8. Saves model.pkl only (no scaler.pkl)

Training label mapping: 0→CALM, 1→ANXIETY
Training baseline: fixed HR=75, GSR=500 (not dynamic)

## Summary Description
> This is a real-time anxiety-state monitoring dashboard that ingests HR and GSR data, calibrates a personal baseline, extracts physiological features, combines rule-based and ML inference, stabilizes the result with smoothing and a finite state machine, and streams the final state to a live Flask frontend.
